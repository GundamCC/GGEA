# 正式发布入口迁移

## 入口与当前状态

GGEA 主仓库统一承载源码、Issues、版本标签和后续正式 Release。迁移版源码为 1.3.4.0；尚未打包、推送或发布，不能把源码版本当成已发布版本。主仓库尚无正式版时，已有正式下载仍位于 [GGEA-Release](https://github.com/GundamCC/GGEA-Release/releases)。

新版客户端只访问 `GundamCC/GGEA` 的最新正式 Release，并严格绑定同仓库、同标签的 ZIP 与校验文件。主仓库缺少正式版时检查会失败，不伪报“已经最新”，也不自动回退到旧仓库。网站可以在确认主仓库存在但尚无正式版时展示经核验的旧仓库版本；网络失败、限流和不完整发布不会触发该回退。

新版来源发现地址为 `https://raw.githubusercontent.com/GundamCC/GGEA/main/update-sources.json`。旧版继续读取 `https://raw.githubusercontent.com/GundamCC/GGEA-Release/main/update-sources.json`。两处保留 v1 协议，初始均为空列表；空列表会清空远程来源缓存，但不影响独立的本地导入配置。此文件仅提供备用源清单，不是主仓库重定向。以后增设备用源时，应分别核验两处配置的服务对象和协议，不能把 GitHub Release API 填为静态版本清单。

## 获得发布授权后的执行顺序

1. 提交并推送已验证源码和根目录来源文件；确认主仓库对应提交及版本。遵守正常发布脚本的干净提交、版本、资源、摘要、ZIP 清单与 EXE 自检要求，生成唯一一份正式过渡包。迁移准备本身不执行这些远程操作。
2. 在主仓库为实际打包的源码提交创建对应版本标签及正式 Release。上传精确命名的 `GGEA-v四段版本-win-x64.zip` 与同名 `.zip.sha256`，校验文件内的包名须一致；不得仅重命名校验文件而保留旧包名。附件先准备完整再公开，核验发布页、API、两个附件、字节数及摘要。
3. 在 GGEA-Release 发布同版本过渡 Release，上传与主仓库字节完全一致的两份附件，并说明后续正式源已迁移。旧仓库标签不代表主程序源码，发行说明必须链接主仓库实际源码标签/提交；`build-info.json` 保持同一源码提交。不能放仅有跳转链接的 Release，也不能给旧客户端返回主仓库附件地址。
4. 用实际已发布旧客户端验证：旧仓库发现过渡版 → 下载与摘要校验 → 安装并保留配置及插件 → 新程序访问主仓库与新来源文件。再验证新版正常检查、网络失败、缺附件和取消路径。现有自动测试只验证请求、解析及文件事务，不能替代真实旧包升级验收。
5. 运行网站 `npm run sync:release`，核验快照来源切换到 GGEA，再执行类型检查、测试及构建。部署网站单独遵守部署授权；源码提交不等于网站已上线。
6. 过渡链路确认后，后续常规 Release 仅在 GGEA 发布。旧仓库继续保留过渡包、原有可用下载、来源发现文件与导航说明，供长期未升级的用户使用；不删除旧下载，不自动归档或关闭仓库。

若任一步失败，保留已有可用发布与兼容入口，停止后续切换，不修改历史附件地址或假称迁移完成。历史已下架版本不因本次迁移恢复。新旧仓库发布、Tag 和部署均需明确授权。

## 仓库边界

- GGEA：主发布源、新客户端固定地址、来源发现、中文与日文产品说明。
- GGEA-Release：兼容导航、旧客户端来源发现和今后的过渡包；历史发布不改写。
- GGEA-website：主仓库导航、发布数据同步及迁移期旧版下载；只展示真实验证过的附件。
- GGEA-Extensions：插件 API、最低宿主版本、独立版本和安装流程不变，本次无需修改或重新构建。
